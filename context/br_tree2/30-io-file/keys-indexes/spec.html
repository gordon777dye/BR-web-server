Keyed access & the index facility

Building and using index (key) files for fast record access by key value. The OPEN/READ/REWRITE statements are in statements; access-method concepts in file-model; record layout in form-spec.

Semantics

How it works

An index/key file holds each master record's key value plus its relative record number (binary B 4). To fetch by key, BR binary-searches the index, gets the record number, and jumps straight to the master record — no sequential scan. Reading a keyed file without a KEY= clause returns records in key order (a free sort).

  • Key field: up to 6 non-contiguous sections (a split key), ≤128 bytes total.
  • Index types: Btree2 (the default for new indexes, ~25–35% faster shared I/O, BTREE_VERIFY <master>[ OFF] audits structure after each index-altering op), Btree (OPTION 22 makes new indexes Btree), ISAM (OPTION 5 = 4). The option decides only what a new index is made as (INDEX, INDEX … REPLACE, an OPEN that creates the key file); each index records its kind in its header and is opened as that kind whatever the option says. One master may have Btree and Btree2 indexes open and updated together. INDEX … REPLACE converts an index to the kind the option asks for.
  • Btree2 locking (5.01): a shared Btree2 index has no lock for the whole of it; each index record has its own. A read holds each record it passes through only until it has the next one, an update only the records it changes (usually one), so sessions wait only for one using the same part of the index. NOSHR takes no locks. Version 3: 5.01 makes Btree2 indexes version 3 (each index record ends in a 4-byte link for its free lists). A version 2 index, made by an earlier release, is read but not updated: error 0633 until INDEX ... REPLACE (or REORG, which rebuilds it) makes it version 3. Earlier releases refuse version 3 with error 4124, so rebuild Btree2 indexes and upgrade every engine together.
  • Primary vs overflow area: INDEX … REORG sorts the overflow (recently added/changed) into the sorted primary area.

INDEX command (create/rebuild)

INDEX <master-file> <key-file> <key-positions> <key-lengths> [<work-path>]
      [REPLACE] [REORG] [VERIFY] [DUPKEYS] [LISTDUPKEYS] [BADKEYS] [LISTBADKEYS]
      [ '>' <output-file> ] [NATIVE]
  • Positions/lengths use / to separate up to 6 sections; append Y for BASEYEAR (Y2K) date handling (23Y; for binary date fields 2BY).
  • REPLACE rebuilds; VERIFY checks a Btree2 index (below); DUPKEYS/LISTDUPKEYS and BADKEYS/LISTBADKEYS control duplicate/invalid-key handling (BADKEYS = Y2K/baseyear keys whose master field holds non-numeric data; with both, bad keys list before dup keys); >file redirects the list. Parameters may be separated by spaces or commas; key fields may overlap.
  • REORG reorganizes the index directly (no master read) — fast, since the already-sorted part is skipped. It does not add new records (keep the overflow current by opening the index whenever you write the master). It fully rebuilds only when the index is absent, isn't an index file, or the stored key positions/lengths differ from those given. For a Btree2 index, REORG repairs instead (below).
  • Btree2: VERIFY and REORG. VERIFY runs while programs use the index (no exclusive access). It checks key order, that no record is reached twice, that every live master record's key is present, and that no update was left unfinished. Anything that looks wrong is rechecked once any update of that part has finished, so updates in progress are not reported. Clean: no error, and an old <index file>.flaws is deleted. Otherwise error 9401, the flaws are written to <index file>.flaws (a first line VERIFIED, then one per line, kind first: OUT_OF_RANGE, STALE_REF, SEPARATOR, MISSING, INTERRUPTED, EXTRA, DISORDER, DAMAGED, DEPTH, TWICE, STRUCTURE), and the index is marked as needing repair. Freed index records are set aside, not reused, until it is repaired. REORG also runs while programs use the index. It checks the ranges a VERIFY-written .flaws names (or everything, master file included, without one or with one only reads wrote; btree2_create deletes an old one), repairs them in place (locking only the index records it changes; a missing key under its master record's lock), rewrites a DISORDER index record (keys out of order or repeated) with its in-range keys in order, once each, keeping only those its master records still have (each checked under that record's lock), removes the link to an unusable (DAMAGED) or too-deep (DEPTH) index record and frees what was below it, removes a second link to a record reached TWICE, removes EXTRA keys (record deleted or keyed otherwise), adds missing keys (scanning the whole master file after removing such a link), puts the records set aside on the free list, then clears the mark and deletes .flaws. Records that stay locked: error 0061, mark and .flaws kept for a later REORG. It does not shorten the file; REPLACE rebuilds an index at its smallest. A DAMAGED/DEPTH removal needs the master file to restore the keys; without it REORG ends with the master file's error, the index still marked for repair. When the index cannot be repaired (STRUCTURE: its first index record is unusable), it rebuilds it from the master file as REPLACE does, which needs the index to itself (a file-sharing error while it is open elsewhere). That rebuild accepts duplicate keys as DUPKEYS does: a WRITE never refuses a duplicate in a Btree2 index, so the index it replaces can hold them.
  • INDEX performs an implicit CLEAR (unless a program is active), runs from READY mode / a procedure / EXECUTE, can be interrupted with Ctrl-A and resumed with GO; -N suppresses the action log.

Opening for keyed access

! existing keyed file (no RECL/KPS/KLN)
00500 OPEN #5: "NAME=ACCT.INT,KFNAME=ACCT.KEY", INTERNAL, INPUT, KEYED
! new keyed file (include RECL, KPS, KLN)
00100 OPEN #1: "NAME=ACCT.INT,RECL=31,KFNAME=ACCT.KEY,KPS=1,KLN=4", INTERNAL, OUTIN, KEYED

A master file may have multiple index files (different KFNAME, different channels, same master name; consistent share params).

KEY vs SEARCH

Clause Match
KEY=k$ exact; k$ length must equal KLN (else error 0718); NOKEY if absent
KEY>=k$ exact, else next-higher key
SEARCH=k$ partial (leading substring) allowed
SEARCH>=k$ partial, else next-higher

Keyed I/O

  • READ #n, KEY=k$: … NOKEY <ref> — fetch by key.
  • RESTORE #n, KEY>=k$: / SEARCH>=… — position for a sequential keyed scan.
  • A sequential read (forward or PRIOR) goes on from the last key it read. That holds even when other sessions, or another channel of the same program, have added or deleted keys since. On a Btree2 index it stays in key order, gives each key once, and misses none that was there throughout. A key added or deleted meanwhile is met or not, according to where it falls. A next key that points at the record just read is passed over, as a deleted record's key is, so the same record is never read twice in a row. An index update stopped part way can leave a key in two places until INDEX ... REORG repairs it.
  • REWRITE without KEY= updates the last record read (fast); with KEY= it searches first (slower). Changing the key field value is allowed — BR automatically updates all related key files opened as a group (the old error 0059 is deprecated).
  • DELETE #n, KEY=k$: — of the key parameters only KEY= is allowed, not KEY>= or SEARCH=/SEARCH>=, because a delete has to name one record and not the next-greater one. It does also take REC=, LINK= and the positional five — see statements.
  • READ #n, KEYONLY: key$, recnum reads the key + relative record number from the index without touching the master record (faster sequential key scans; returns the key when the master record is locked). Valid only for INPUT KEYED/OUTIN KEYED; a master record must have been read first (else error 0718); use FORM of key length + B 4; it moves the master pointer but a following REREAD/DELETE/REWRITE errors. Keep the key file current or it may return a stale record number.
  • Functions: KPS(n), KLN(n), KREC(n) — key start position, key length, and last index-file record accessed; all return -1 if the file isn't open keyed. KLN(n,seg) (and KPS(n,seg)) give a split-key section's length/position — seg=0 (or omitted) is the total combined length, a too-large seg returns -1. KREC(n) is the last record in the index/key file, not the master (that's REC(n)); for a display file it's instead the line counter since the last NEWPAGE (same as LINES(n); NEWPAGE; with a trailing ; suppresses the reset). In a linked file KREC tracks an anchor record only when REC=<anchor> is processed or an anchor is read/written/ deleted; RESTORE REC=<non-anchor> sets it to 0.

Duplicate keys

All KEY= forms return the first match (lowest record number); read sequentially to walk the rest, stopping when the key changes:

00100 READ #1, KEY="JONES": NAME$, ADDR$, AMOUNT
00110 DO
00120   READ #1: NAME2$, ADDR2$, AMT2 EOF DONE
00130   IF NAME2$ <> "JONES" THEN EXIT DO
00140   ! process duplicate
00150 LOOP

Tables — error codes

Code Meaning
4272 NOKEY — key not found
0718 key string length mismatch
0059 (deprecated, 2.x only) attempt to change key field value — changing a key is now allowed
7603 duplicate keys found (warning)
7611 key file already exists (no REPLACE)

Examples

! Build a split-key index: name (1-20) + zip (50-54)
INDEX CUSTOMER.DAT CUSTZIP.KEY 1/50 20/5 REPLACE

! Read July–August by key range
00410 OPEN #3: "NAME=MILES.DAT,RECL=24,KFNAME=MILES.KEY", INTERNAL, INPUT, KEYED
00420 READ #3, USING 430, KEY>=070196: DATE, MILES, GALLONS, MPG
00430 FORM N 6, N 6.2, N 6.2, N 6.3
00440 DO WHILE DATE < 090196
00460   READ #3, USING 430: DATE, MILES, GALLONS, MPG EOF 480
00470 LOOP
00480 CLOSE #3:

! Rebuild after batch updates
99000 EXECUTE "INDEX ACCT.INT ACCT.KEY 1 4 REPLACE"
