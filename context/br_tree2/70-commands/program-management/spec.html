Program management & procedures

Loading, saving, running, and chaining programs, plus procedure files (command scripts). Commands run immediately (no line number) and — crucially — from program code via EXECUTE. Line-editing commands are in editing; file/dir commands in file-directory.

Command vs statement

A command executes immediately when typed (no line number) and manages the environment (LOAD, SAVE, RUN, LIST, DIR). A statement has a line number and runs at RUN. Any statement can be run immediately as a command; a bare expression is an implied PRINT (6+4→10). Commands can't appear in a program except via EXECUTE or inside a PROC.

A PRINT typed at the command line can send its console output to a file or string array with | > and | >>: see PRINT ... | > file in the printing statements.

-? — what a command takes (BR 5.0)

Any command given -? as the whole of its arguments lists the forms and options it accepts and does nothing else: COPY -?, LIST -?, STATUS -?. Nothing runs, so RUN -? loads nothing and SYSTEM -? does not leave BR. -? alongside other arguments is not the help: COPY a.txt -? is a COPY with an unknown option, a syntax error, and a LIST search string containing -? is a search. A long list pauses after each screenful (any key goes on, Ctrl-A stops). DIR -? lists the options of the listing in use — the 5.0 ones, or the 4.x ones under OPTION 8. Every command in BR's command table has it except HELP (and the internal LINK). The lists are written from each command's parser, so where this tree and -? differ, -? is the one that matches the code.

Entry & exit

BR [<instructions>] [-<id>] [-<config>] [-<ref>]   -- start BR (optionally run a command / set WSID / config)
SYSTEM | SY                                         -- exit BR to the OS (closes files)
SYSTEM <integer>                                    -- exit to the OS, returning <integer> as the process exit code
SYSTEM LOGOFF [ALL]                                  -- exit BR and log the client off (ALL: every session slot)
SYSTEM [<flags>] "<os-command>"                      -- run an OS shell command, then return to BR

SYSTEM — exit BR / call the OS shell

SYSTEM is a command (not a primary-op statement); a program reaches it via EXECUTE or a PROC. Three forms:

  • Exit — bare SYSTEM (SY) closes files and returns to the OS; SYSTEM <n> returns <n> as the process exit code (readable by a calling shell/script: ERRORLEVEL in a DOS batch file, $? in a Linux shell). SYSTEM LOGOFF [ALL] exits and also logs the client off — see logoff.
  • Shell call — SYSTEM "<os-command>" runs an operating-system command (launch another program, run a script), then returns to BR — the program's main way to invoke other applications through the OS. This is consequential for app development and for security review (it executes arbitrary OS commands with the caller's privileges).

Shell-call flags precede the command string and are case-sensitive (an unknown flag → error 4501; conflicting flags → flag-conflict error):

Flag Effect
-@ run the command on the BR client side
-S / -s run on the BR server side (default follows the SHELL DEFAULT CLIENT/SERVER config)
-R / -r (or leading *) restore the BR screen after the call
-C / -c continue asynchronously — don't wait for the command to finish (conflicts with -R). Windows launches the task and BR carries on; on Unix the command is framed with NOHUP and &. Without it the call waits for the process, up to the SHELL LIMIT seconds
-M / -m hide / minimize the launched program's window
-H / -h hide / minimize BR's own window during the call
-W / -w accepted and ignored in BR 5.0 (it marked a Windows program in 4.x, and no longer conflicts with -R)
-E / -e permit a shell-call error to be reported/trapped
-P / -p page
-T/-t<secs> override the shell-call timeout
+<n> accepted and ignored (it once requested <n> of memory for the child)

(SYSTEM ONQ … is an ordinary shell command in BR 5.0: the built-in ONQ interface was removed.)

SYSTEM LOGOFF / SYSTEM LOGOFF ALL

SYSTEM LOGOFF is an exit form: it ends BR exactly as bare SYSTEM does (files closed, exit code 0). It is subject to the same rule as the other exit forms: keyed at the console while a program is active, it fails with error 2108 ("program is active"). Before exiting, it flags the client to log off. The logoff then runs when the client shuts down, and it removes what a logon leaves on the workstation:

Cleared Scope
The persistent-login session id (registry ClientServer\sessionId_<listener port>) machine
The login dialog's AutoLogin and Remember me settings machine
The saved Windows credentials machine
The session table entry — WSID, window handle, window class name, process time this session's slot only (SYSTEM LOGOFF) or all nine slots (SYSTEM LOGOFF ALL)

In client-server mode the client also tells the listener to drop this session's multisession login, so the next connection must log on again.

The machine-wide items are cleared by both forms. ALL only changes the session table.

  • Plain SYSTEM LOGOFF frees only this session's slot and leaves the other eight as they were.
  • SYSTEM LOGOFF ALL zeroes every slot. That includes the WSIDs of sessions that are still running, which is why it is not the default. It is the recovery for a slot left unusable — for example when Windows reports another session's window as still live, so that session's WSID is never freed and WSIDs get assigned wrongly.

Parsing:

  • LOGOFF and ALL are case-insensitive. ALL must be spelled in full and be a whole word (followed by a space, a tab or the end of the line). SYSTEM LOGOFF ALLOCATE is therefore plain SYSTEM LOGOFF.
  • Nothing else after LOGOFF is read. A number there is not an exit code: SYSTEM LOGOFF 5 still exits with 0.

Program lifecycle commands

Command (abbrev) Action
LOAD f [SOURCE|OBJECT] (LO) clear memory, load f; see loading for modes & extensions
SAVE f [SOURCE] (SA) save to a new file (error 4150 if exists)
REPLACE [f] (REP) overwrite an existing file (keeps a .bak)
RUN [<program>] [PROC] [STEP|TRACE] (RU) execute from the lowest line (resets vars); with <program>, load it first. PROC takes input from the running procedure (see run-proc); STEP/TRACE → information
MERGE f [-<from>] [-<to>] [<first>|ADD] (ME) merge program lines from a file (see merge)
CLEAR [PROC|RESIDENT|ALL] (CL) clear program/vars/procedures/libraries (see clear)
GO [RUN][STEP][TRACE][.<line>] resume / step a halted program (see go); GO END terminates it
STOP halt execution (also a statement)

Loading & the default extension

LOAD (LO) clears memory, then loads. SOURCE loads an ASCII .brs program line-by-line as if typed (syntax-checked per line; on a syntax error BR halts for a fix — unless PROCERR RETURN is active in a procedure, which instead returns the code in ERR and the failing line in LINE so a SKIP can test it). OBJECT loads the .bro object; RESIDENT loads the file as a resident library. The mode is set by the keyword, not inferred from the extension: LOAD defaults to object, so loading a source program requires an explicit SOURCE — LOAD "prog.brs" SOURCE. Naming the .brs file alone (LOAD "prog.brs") does not trigger source mode; BR tries to read it as an object file and fails. Extension search: a bare name tries .BR then .BRO (.BRS for SOURCE), overridable via CHAINDFLT in BRConfig.sys; a trailing period (LOAD NAME.) suppresses the search and loads the name as-is. A failed LOAD leaves memory intact.

MERGE

MERGE f [-<from>] [-<to>] [{<first>|ADD}] (syntax mirrors RENUM) pulls lines from another .br into memory. With no first/ADD, merged lines keep their numbers and replace any existing lines that share them. ADD appends all lines after the current program's last line; <first> renumbers the first merged line (others follow the source increments). A single line number merges only that line.

  • Defaults: the whole program is merged; a -<from> alone merges from that line to the end of the program; the merged lines keep their numbers. Caution: a merged line replaces any line in memory that has the same number.
  • f is the name of the program (a .br file) to merge.
  • <first> is the number given to the first merged line; the others follow the increments the source file had.
  • ADD puts every merged line after the end of the program in memory: the first is numbered ten greater than the current last line, and the rest keep the source's increments.
  • Examples: MERGE MERGETST -100 -300 merges lines 100 to 300 of MERGETST.BR, keeping their numbers (and replacing any lines of those numbers in memory); MERGE MERGETST ADD adds all of MERGETST.BR to the end.
  • Behaviour change: MERGE f <line> with a line number alone merges only that line. Before it merged from that line to the end of the program, which may matter to an old application.
  • To look at lines of another program without merging them, use LIST <name (see LIST).

SAVE / REPLACE — source vs object

SAVE writes a new file (error 4150 if it exists); REPLACE overwrites an existing one and leaves the lines in memory. Saving as source stores the current STYLE formatting with the file, permanently. Both save source only when the name ends .BRS or the SOURCE keyword is given; otherwise they save object (.BR/.BRO). With no filename, REPLACE reuses the file's full original name (a trailing period suppresses the default extension). OBJECT (.BRO) omits source — unrecoverable, used to ship protected code. Before overwriting, BR copies the original to .BAK (recoverable until the next REPLACE); OPTION 26 suppresses .BAK creation. End execution before REPLACE; to save without ending, LIST >tmp then LOAD it from source.

Which object format is written. BR 5.0 writes save level 39, which records for each statement the source file line it came from. BR 4.2 and 4.3 wrote level 38, which has nowhere to keep that. A BR older than 5.0 given a level 39 program refuses it with error 2240 (release level error) rather than misreading it; BR 5.0 loads either level, and a level 38 program simply has no source line positions in it.

OPTION 60 makes SAVE and REPLACE write level 38, so a program can be read by a 4.2 or 4.3 BR - at the cost of those positions. It also sets OPTION 74. The 4.18-and-earlier format this option used to write is no longer written at all, though programs already in it still load. OPTION 60 governs saving only: BR 5.0 loads the pre-4.2 format, level 38 and level 39 alike, set or not.

CLEAR

CLEAR (CL) with no argument clears the program for new entry. ALL ends the program, closes all procedures and clears memory. PROC closes all procedures but keeps memory (variables remain for debugging); PROC ONLY additionally keeps the program running. RESIDENT clears all resident libraries ("name" clears one, and so does CLEAR name without RESIDENT); adding STATUS instead demotes resident → present rather than unloading — but only while a program is halted; otherwise STATUS is read as RESIDENT. CHAIN and LOAD perform an implicit CLEAR.

GO — resume / step

GO [RUN] [STEP|NOSTEP] [TRACE [PRINT]|NOTRACE] [.<line>] resumes a halted/interrupted program with all variables and open files intact. RUN first clears prior STEP/TRACE settings; STEP pauses before each action statement, TRACE echoes line numbers (PRINT → printer). GO <line> resumes at a line; GO .<line> runs until a line then issues a STEP interrupt (GO .5280:2 stops before line 5280 clause 2; a bare GO . reuses the last temp breakpoint; GO with no period clears it). After an error, GO retries the failing statement. In STEP mode, Shift+F1–F5 step with widening scope (into-clause / over-clause / into-line / over-line / to RETURN|FNEND). GO END terminates the interrupted program and closes all files.

  • A line can be given as a line label as well as a number, for both GO <line> and GO .<line>.
  • The TRACE output goes to the screen unless PRINT is given; PRINT works only with TRACE. For example GO TRACE PRINT 1350 resumes at line 1350 and traces to the printer. NOSTEP and NOTRACE turn the two off.
  • STEP shows the number of the line about to run in the status line; Enter runs it and shows the next. In STEP mode a typed GO means GO RUN and Enter means GO STEP. RUN STEP NORESTORE stops BR putting the application screen back after the first time; RUN STEP RESTORE puts it back before every step (and GO RUN does not reset NORESTORE). GO PROC takes the program's input from the active procedure.
  • TRACE SOURCE shows each line's source text as it runs, in place of only its number.
  • Shift+F1 to Shift+F4 step by a wider scope each time: the F-key number rises as the scope does.

AI (BR 5.0)

AI NEW
AI <text>

At the READY prompt, AI followed by what you want opens a conversation with an assistant attached to the session's channel. The reply prints in the HILITE colour; the commands the assistant asks to have run are marked [AI] >. AI NEW starts a fresh conversation. With no assistant listening the command stops at once with error 4158.

  • A turn is the person's to open. It needs an open turn, not the keyboard grant; anything destructive stops and asks. The assistant itself may not use AI (error 4171).
  • A running program or procedure must consent: set ENV$("AI_TURN_OK") to "Y" first (LET X=SETENV("AI_TURN_OK","Y")), or AI is refused with error 4169. AI NEW needs no flag.
  • A break key halts the wait at READY with the turn still open, and GO resumes it; CLEAR PROC and CLEAR ALL end a turn.
  • AI=5 still assigns to a variable called AI; only AI followed by a space is the command.

EXECUTE — run a command from code

EXECUTE "[*]<command-string>"

Runs any command/statement string at runtime — the bridge that makes commands part of the coding surface (build index files, run a SORT, start a PROC, …). A leading * makes BR save the screen and put it back when the command finishes; without it the screen is not restored (EXECUTE "DIR" leaves what the command wrote, EXECUTE "*COPY OLDFILE NEWFILE" restores the screen). In GUI mode the screen is never saved, so the * has no effect there. Inspect CODE afterward for a procedure's return value. Restrictions: because it is illegal to terminate a program from EXECUTE, the program-ending commands LOAD, SAVE, REPLACE and the CHAIN statement may not be used inside it. This LOAD restriction applies to a LOAD that replaces the running program; LOAD ...,RESIDENT (loading a resident library) does not terminate the current program and is allowed. INDEX/SORT can be started from EXECUTE (no prior CLEAR, so less memory — may run slowly; out-of-memory → error 7607/7811). All errors (including command syntax errors) are passed back, trappable with ERROR/IOERR/Exit; an EXECUTE may itself be the subject of another EXECUTE.

CHAIN — end this program, start another

CHAIN { "<program>" | "PROC=<name>" | "SUBPROC=<name>" } [, { FILES | MAT <array> | <var> }]…

CHAIN (a statement) ends the current program and loads/runs another program, or starts a procedure. By default it closes all files (except procedure files) and resets the new program's variables; FILES keeps files open at their current positions (pointers are not moved — use RESTORE to reposition), and trailing MAT array/var names carry those values into the chained program (dimensions needn't match; the caller's win). FILES may stand at any of those comma-separated positions, not only the first — chain A$, XXX, FILES is accepted. The program name follows the same default extension rules as LOAD (.BR→.BRO, CHAINDFLT). "PROC=…" ends the program and starts a procedure (closing the lowest active proc first); "SUBPROC=…" starts a nested procedure without disturbing the running one — both keep the terminated program in memory so its variables stay available to the procedure. CHAIN "PROC=XYZ" is like EXECUTE "PROC XYZ" except CHAIN ends the program. Procedure files

A procedure is an ASCII (DISPLAY) text file of commands run in order — one command per line, ! comments, :label branch targets, no line numbers, up to 800 chars/line. A .$$$ extension makes it self-deleting after execution.

Starting: PROC {name|*name|ECHO|NOECHO} (runs it; * suppresses F2 logging; NOECHO hides lines). SUBPROC file runs a nested procedure (up to 9 deep) then resumes. From code: CHAIN "PROC=…" / CHAIN "SUBPROC=…" (ends program) or EXECUTE "PROC …" (keeps program running). RUN PROC feeds procedure lines to a program's INPUT/LINPUT/RINPUT; it has no effect on INPUT FIELDS or RINPUT FIELDS.

RUN … PROC — PROC is an option of RUN, not a command. It is not followed by a file name: the lines fed to the program are the ones that follow the RUN line in the procedure that is already running. Two forms work, both only as lines inside a procedure:

RUN <program> PROC           ! load <program>, then run it with proc-fed input
LOAD <program>               ! or: load first ...
RUN PROC                     ! ... then run what is in memory with proc-fed input
  • Outside a procedure (typed at READY, or as the startup command-line argument) RUN … PROC fails with error 2103, "illegal PROC parameter".
  • RUN PROC <file> does not name a proc file. RUN's first word is checked against its options before being read as a program name, so PROC is taken as the option and no program is loaded. <file> never becomes a program name. With nothing in memory, BR reports error 2104 (no active lines).
  • A plain RUN inside a procedure does not feed it. PROCIN stays 0 and the program reads the keyboard; under UNATTENDED logging it aborts at its first input statement.
  • How the lines are used. Each input statement consumes the next proc line. When the program ends, the following proc lines are commands again. Confirmed on 4.33c.
  • The RUN … PROC line must not be the proc's last line. See look-ahead.

Flow & errors: SKIP n|label [IF <cond>] branches — the label is written without its colon (SKIP BUSY goes to the line :BUSY; SKIP :BUSY never matches), and a label search that reaches the end of the procedure carries on from the top, so a skip may go backward; PROCERR STOP (default) halts on error and PROCERR RETURN continues (sets ERR); ALERT msg pauses for the operator (GO resumes; under PROC NOECHO the message shows but the operator must press F2/F3 to see the command — bracket ALERT with PROC ECHO…PROC NOECHO); CLEAR PROC / CLEAR ALL close procedures.

Look-ahead close: BR closes a procedure before executing its last line, so that line behaves as an independent one-line command — it cannot be a SKIP that branches backward or a RUN PROC (the file is already closed), and shouldn't be error-prone; add a blank/comment line if you need the proc to stay open. This look-ahead is what lets a .$$$ proc (or one whose last line is FREE) delete itself, and avoids stacking an extra open file. Each active procedure counts as one open file; nesting goes 9 deep (status-line columns 58–59 show P1…P9), and RUN PROC feeds procedure lines to a program's INPUT/LINPUT/RINPUT — one proc line per input statement (too many/few lines causes unpredictable misreads; PROCIN → information tells the program input is coming from a proc).

Express procedures run during a program via EXECUTE "PROC …" / "SUBPROC …" (or operator-keyed during an interruption): they imply NOECHO, are subordinate to the running program, and resume it when done. An error in an executed express proc closes the proc and returns to the EXECUTE statement's error trap. EXECUTE "PROC XYZ" cancels the last-activated proc (and ends any RUN PROC input mode); EXECUTE "SUBPROC XYZ" preserves the hierarchy (and keeps RUN PROC active). A program can shed one procedure layer by running an empty express PROC. The full procedure-system reference (start methods, syntax rules, express-vs-standard chart) is retained in Procedure_files.

Examples

04200 EXECUTE "PROC DAILY"            ! start a procedure, program keeps running
99000 EXECUTE "INDEX ACCT.INT ACCT.KEY 1 4 REPLACE"
00900 CHAIN "proc=MONTHEND"           ! end program, run procedure

A procedure that runs a program with its input supplied (PROCIN returns 1). Start it with PROC nightly.prc. The program's first input statement reads FIRST-ANSWER and its second SECOND-ANSWER. When the program ends, SYSTEM runs as an ordinary command:

RUN myprog PROC
FIRST-ANSWER
SECOND-ANSWER
SYSTEM

! procedure: purge deleted records safely (multi-user)
PROCERR RETURN
PROTECT CUST.FIL,RESERVE
SKIP BUSY IF ERR<>0
COPY CUST.FIL TEMP[WSID].FIL -D
RENAME TEMP[WSID].FIL CUST.FIL
PROTECT CUST.FIL,RELEASE
SKIP DONE
:BUSY
ALERT File is busy, try again later -- type GO
:DONE
RUN MENU
